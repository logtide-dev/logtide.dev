This release adds hardware health to the monitoring area. It is aimed at bare-metal servers and homelabs, where a failing disk or a DIMM that keeps logging corrected errors usually gives some warning before it takes the machine down. The data comes from a small agent that now lives in its own repository, [logtide-dev/logtide-hw-agent](https://github.com/logtide-dev/logtide-hw-agent), released separately starting at 1.0.0. The setup is described in [Hardware Health](/docs/hardware-health/), and the blog has a [step by step tutorial for a home server](/blog/monitor-home-server-hardware-health/).

**Before upgrading:** migration 079 runs on startup. It adds the `hardware_hosts` table and lets incidents come from the new `hardware` source. Nothing changes for existing data. To collect hardware data, start the agent with the new compose profile (`docker compose --profile hardware up -d`) and set `HW_AGENT_API_KEY` to a project API key, or install the agent as a systemd service.

### Added

- **Hardware health**: a new Monitor > Hardware section (shortcut `g h`) that watches the physical health of a host and warns before a component fails. It covers disks (SMART for HDD and SSD, the NVMe health log: reallocated and pending sectors, uncorrectable and media errors, wear, spare, temperature), ECC memory (corrected and uncorrected errors per DIMM from EDAC), CPU (temperatures against their limits, thermal throttling), cooling (fans and board temperatures), power (PSU state and redundancy, voltages) and physical network ports (CRC errors, link flaps). Each host gets a status per component, the findings that explain it and 7 day trends.
- **Hardware agent**: a small agent written in Python with no dependencies, shipped as the Docker image `logtide/hw-agent` or as a systemd unit. It reads smartctl, EDAC, hwmon, thermal throttle counters, IPMI sensors and the BMC event log, and sends them as OTLP metrics with the project API key. Hardware lines from the kernel log and BMC events are sent as logs under the service `hardware`.
- **Trend-based rules**: a disk that reallocated 10 sectors in a week or a DIMM that logs corrected errors every day is flagged even while SMART still says "passed". A device that stops reporting, such as a disk dropping off the bus or a pulled power supply, is a finding too. A change has to hold for a few minutes before it counts and a recovery for 10 minutes, so a sensor hovering around its limit does not flap.
- **Incidents and notifications**: a degraded host opens an incident with the new source `hardware` and notifies through the new `Hardware health` event type in notification routing: channels, email fallback, PagerDuty and the webhooks `hardware.health.degraded` and `hardware.health.recovered`. Owners and admins can mute a host or forget it.
- **Hardware Health detection pack**: Sigma rules for kernel and BMC hardware events, such as ECC and machine check errors, APEI, disk I/O errors and link resets, NVMe timeouts, PCIe AER, thermal and power supply events. It works on any kernel log shipped to LogTide, with or without the agent.
- Virtual machines are detected and shown as "No sensors", because a VM does not expose hardware sensors.
- New capability `hardware.max_hosts`, unlimited by default.

### Changed

- **Clickable rows in traces**: in Traces a click anywhere on an Operations row filters on that operation, and a click anywhere on a trace row opens the trace. Ctrl or middle click opens it in a new tab.
- **Shorter operations list**: the Operations card shows the 8 slowest operations with a "Show all" toggle, so the trace list is no longer pushed far down the page. A selected operation stays visible.

### Fixed

- **Login page while signed in**: opening `/login` or `/register` with an active session now goes to the dashboard instead of showing the sign-in form, which looked like being logged out.
